Naming the Bundle

Background

A Home Assistant dashboard is built from cards. Some ship with HA; the rest are custom cards — JavaScript files a user registers as a Lovelace resource, after which the card's tag can be used in a dashboard. Most people install them through HACS, a community add-on store that downloads a card's release asset from GitHub and drops it into /hacsfiles/<repo-name>/.

This repository, ha-card-shared, is not itself a card. It is the shared toolchain four sibling card repos install as a dev dependency: one TypeScript config, one Rollup config, one Vitest config, one lint config, plus the reusable CI workflows. A card repo writes its own src/ and inherits everything about how it is built.

The relevant inherited piece is cardBundle() in rollup.base.mjs. A consumer's entire rollup.config.mjs is two lines:

import { cardBundle } from "ha-card-shared/rollup.base.mjs";
export default cardBundle();

That function returned a config whose output file was the string literal "dist/card.js". Every one of the four cards therefore built a file with the identical name. Nothing was broken by this — HACS keeps each card in its own folder, so the paths never collided — but the name carried no information.

The nuance that makes this worth a change: the folder disambiguates the file on disk, but the resource URL is what a user reads and edits in the HA settings UI. With five cards installed you see five entries ending in card.js, and the only distinguishing part is a directory name several segments back.

The idea

The fix is one line. cardBundle() already accepted a name option, defaulting to process.env.npm_package_name — the package name npm exports into the environment of any npm run script. That name was used for the banner comment at the top of the bundle, and nowhere else. It just had to reach the filename too.

package.json name → npm run build sets npm_package_name → cardBundle() default → dist/<name>.js

Concretely, for the scoreboard card:

before
/hacsfiles/ha-teamtracker-scoreboard-card/card.js

after
/hacsfiles/ha-teamtracker-scoreboard-card/ha-teamtracker-scoreboard-card.js

The interesting decisions were not in the line itself but around it.

Why a fallback rather than an error. The new expression is `dist/${name || "card"}.js`. Run rollup -c directly, outside an npm script, and npm_package_name is simply absent. Failing loudly there would turn a working invocation into a broken one to punish a misconfiguration the bundler cannot fix anyway; falling back to card preserves exactly today's behaviour.

Why the release workflow does not glob. It would have been shorter to upload dist/*.js. But the release asset is the one artifact a mistake reaches users through, so the workflow derives the expected name from package.json and names it explicitly. If the build ever emits something else, the release fails rather than quietly shipping a file nobody expected.

The load-bearing consequence. HACS decides which release asset to install by reading the filename field in a card's hacs.json. Rename the built file without updating that field and HACS installs break for that card's users. This is why the migration recipe puts hacs.json first, ahead of the README and the demo page.

And one effect no repository change can absorb: an existing user's Lovelace resource URL still points at …/card.js, which becomes a 404. They must re-point it by hand. That belongs in each card's release notes.

What changed

The seam — rollup.base.mjs, one line:

- file: "dist/card.js",
+ file: `dist/${name || "card"}.js`,

The test — test/rollup-base.test.ts, three cases: an explicit name, the npm-metadata default, and the absent-metadata fallback. Writing it surfaced a trap worth naming:

// Assigning undefined would store the string "undefined" — delete is the only real unset.
if (original === undefined) delete process.env.npm_package_name;
else process.env.npm_package_name = original;

Everything on process.env is coerced to a string, so process.env.X = undefined leaves the property set to the five characters "undefined" — which is truthy, and would sail straight past name || "card". The fallback test would have been asserting nothing.

The workflows. shared-publish-release.yml gains a step that reads the name out of package.json and feeds it to the upload; shared-deploy-demo-page.yml does the same for the Pages copy:

- name: Derive bundle name from package.json
  id: name
  run: echo "name=$(node -p "require('./package.json').name")" >> "$GITHUB_OUTPUT"

# ...
  files: dist/${{ steps.name.outputs.name }}.js

An unplanned addition. The design called a root-level test free, because coverage include is src/**. True for coverage — but tsc's include is a different list, and it rejected the test with TS7016: rollup.base.mjs is untyped JavaScript imported under strict. The answer is a sibling declaration file, rollup.base.d.mts, rather than a suppression comment, because rollup.base.mjs is an exported entry point — consumers get the types as a side effect. It is listed in package.json's files.

Docs, version, recipe. CLAUDE-SHARED.md, README.md and ship-it/SKILL.md stop saying dist/card.js. The unreleased 2.0.1 drops back to 2.0.0 (neither was ever tagged; v1.4.1 is the latest published release), and the migration recipe is renamed to match, gaining the asset-rename checklist. Its references to scripts/setup-claude.js and hooks/skill-guard.mjs — both moved under harness/ in #31 — were stale, and were corrected while the file was being renamed.

An incidental proof. fixtures/smoke/rollup.config.mjs calls cardBundle({ name: "smoke" }). The smoke build now emits fixtures/smoke/dist/smoke.js, so the repo's existing end-to-end fixture exercises the rename without anyone adding a check for it.

Quiz

Why does `cardBundle()` fall back to `card` instead of failing when the package name is missing?

What breaks for a card's users if it ships the 2.0.0 rename without editing `hacs.json`?

Why does the release workflow derive an explicit filename rather than uploading `dist/*.js`?

In the test, why is `delete process.env.npm_package_name` used rather than assigning `undefined`?

The design predicted a root-level test would be "free". What did that miss?
