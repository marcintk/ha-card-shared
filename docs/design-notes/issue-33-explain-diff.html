Background

When you run npm install, npm executes each package's postinstall script inside your project. It is the one moment a library gets to reach out and configure the repository that installed it. ha-card-shared uses that moment for three things: symlink its bundled Claude Code skills into .claude/skills/, merge its guard hooks into .claude/settings.json, and point git's core.hooksPath at its shared pre-commit / pre-push scripts.

Two details make this delicate. First, postinstall runs on every install, so it must be idempotent — running it twice must leave the same result as running it once. Second, it edits files the consumer also owns and may have edited themselves, so it must merge rather than overwrite.

The script handled both. What it did not handle was a consumer whose repository still carries the shape an older version left behind. Two of the four sibling card repos are pinned to v1.4.1 and have never taken a 2.x upgrade, so they still carry the v1.4.0 layout — and that layout is the input the current script was never written against.

An installer's hardest input is not a fresh machine. It is a machine configured by a previous version of itself.

Two bugs, one mistake

Both failures come from the same habit: the installer asked whether a path had a value, when the question that mattered was whether that value still did anything.

The first. In v1.4.0, a consumer's .claude/settings.json was a symlink pointing into node_modules/ha-card-shared/.claude/settings.json. v2 stopped shipping .claude/ inside the package, so after an upgrade that link points at nothing. The script's next move is writeFileSync on that path — and writing to a symlink follows it, by design.

writeFileSync(.claude/settings.json) → follows link → node_modules/ha-card-shared/.claude/settings.json → parent directory gone → ENOENT → postinstall throws → npm install fails

And the near miss, which is arguably worse: where that parent directory happens to still exist, nothing throws. The merged hooks are written into the package, the install reports success, and the next npm install replaces node_modules and discards them. A guard that silently stops existing is worse than one that visibly breaks.

The second. core.hooksPath tells git where to find hooks. The script refused to touch any value that did not contain the string ha-card-shared — a reasonable-looking way to say “this one is the consumer's, leave it.” But ha-news-card has it set to .githooks, a directory that is empty. Git finds no hook files there, runs nothing, and says nothing.

The consumer has no pre-commit lint, no pre-push coverage gate, and no error message telling them so — and because .githooks will never contain the string ha-card-shared, no future upgrade would ever have repaired it.

A string test was standing in for a much bigger claim: the consumer owns working hooks here. Checking a config value is not the same as checking that the value does something.

What changed

Look before writing. A symlink is dropped when it dangles or resolves inside node_modules — and left alone otherwise, so a consumer pointing the file at their own dotfiles keeps that arrangement:

function dropPackageSymlink(settingsPath) {
  let link;
  try { link = lstatSync(settingsPath); } catch { return; }
  if (!link.isSymbolicLink()) return;
  let target;
  try { target = realpathSync(settingsPath); }
  catch { rmSync(settingsPath); return; }   // dangling
  if (target.split(sep).includes('node_modules')) rmSync(settingsPath);
}

lstatSync is the key: unlike statSync it does not follow the link, so it can report that the path is one. Dropping the link before the read matters too — otherwise the package's stale copy would be merged into the fresh file.

Ask whether the directory holds hooks, not whether the string looks familiar:

const hasHooks = (p) => {
  try { return readdirSync(resolve(root, p)).length > 0; }
  catch { return false; }   // missing directory
};

if (current && !current.includes('ha-card-shared') && hasHooks(current)) return;

One try/catch covers both the missing and the empty case, since readdirSync throws on the former and returns [] on the latter.

A promise was narrowed, deliberately. README.md said postinstall “won't override a non-ha-card value”, without qualification, and an existing test asserted it. That test set core.hooksPath to .my-hooks without ever creating the directory — the nonexistent path was incidental to what it meant to check, so it now builds a populated directory and still passes. The README carries the exception. Changing an existing test to admit a new behaviour deserves to be named out loud rather than buried.

Five new cases, each red before the fix: the dangling link installs; the resolvable link leaves the package copy byte-identical; a symlink outside node_modules survives; a missing and an empty hooksPath are both taken over. The installer is now covered by seventeen tests.

Beyond the unit tests, the whole thing was run against a faithful reconstruction of ha-news-card — dangling symlink and empty .githooks together. The install succeeds, the symlink becomes a real file carrying all three guard hooks, hooksPath is repaired, and no node_modules/ is created.

Quiz

Why does writing to `.claude/settings.json` end up inside `node_modules`?

Why is `lstatSync` used rather than `statSync`?

A consumer symlinks `.claude/settings.json` to a file in their own dotfiles repo. What happens now?

Why was the old `core.hooksPath` check insufficient?
