Design note · ha-card-shared

Unsticking the installer: symlinked settings and dead hook paths

issue #33 branch fix/postinstall-symlink-and-hookspath drafted 2026-08-29 approved

01Symptom

Two consumers — ha-news-card and ha-yahoofinance-board-card — are stuck on the v1.4.0 layout. Both were found during a harness audit, and both were reproduced before anything was changed.

A — upgrading fails the install outright. Their .claude/settings.json is a symlink into node_modules/ha-card-shared/.claude/. v2 stopped shipping .claude/ in package.json files, so after the upgrade that link dangles. setup-claude.js then calls writeFileSync straight through it — the parent directory no longer exists, so ENOENT propagates out of postinstall and npm install fails.

A′ — the near miss. Where the target directory does happen to exist, the write follows the link and lands inside node_modules/. The install appears to succeed; the merged hooks are then discarded by the next npm install, with nothing said.

B — the git hooks are silently dead, permanently. ha-news-card has core.hooksPath=.githooks pointing at an empty directory, left over from before the shared hooks. Git runs no hook and reports nothing. wireGitHooks bails on any value not containing ha-card-shared, so no future upgrade will ever repair it.

02Root cause

Both bugs are the same mistake in two places: the installer trusts a path without looking at what is actually there. It asks “is there a value?” when the question that matters is “does this value still do anything?”

writeFileSync(path) — follows symlinks by design; never asked whether the path was one

current.includes('ha-card-shared') — a string test standing in for “the consumer owns working hooks here”

03The fix

Two narrow checks, both in harness/setup-claude.js.

Drop the package symlink before writing. lstatSync the settings path; if it is a symlink that either dangles or resolves inside node_modules, remove it so a real file takes its place. A symlink the consumer aims somewhere of their own — dotfiles, say — is followed exactly as before. Removing the link before the read also means the package's stale copy is not merged into the new file.

Treat a hookless directory as a leftover. core.hooksPath is taken over when it names a directory that is missing or empty, because such a value hooks nothing. A real, populated hooks directory of the consumer's own is still left untouched — that promise is unchanged, and now genuinely tested.

A documented promise narrowed. README.md previously said postinstall “won't override a non-ha-card value”, full stop. It now carries the exception. An existing test encoded the old promise using a directory it never created — the nonexistent path was incidental to its intent, so it was amended to build a populated directory, keeping what it meant to assert while the new cases cover the leftover.

04Guardrail

Five cases added to test/scripts/setup-claude.test.ts, each red before the fix: the dangling link installs; the resolvable link leaves the package copy byte-identical; a symlink outside node_modules survives; a missing and an empty hooksPath are both taken over. Seventeen tests now cover the installer.

Verified end to end against a faithful reconstruction of ha-news-card's exact state — dangling symlink and empty .githooks together: the install succeeds, the symlink becomes a real file carrying all three guard hooks, hooksPath is repaired, and no node_modules/ is created.

Correction to the audit that produced this issue. It claimed the harness was “never linted, typechecked, or tested”. Wrong: test/scripts/ and test/skills/ already hold ~500 lines covering this installer, the shared CLAUDE-SHARED.md contract, and render.py. The gap is narrower than stated — issue #35's scope shrinks accordingly, and skill-guard.mjs is the component genuinely without tests.

05Non-goals

Editing the two stuck consumer repos. The fix travels to them on their next upgrade, which is the point — a repair that needs manual intervention in each consumer is not a repair.
