Releasing Without Touching Main

Background

This repository has a rule enforced by machinery, not convention: harness/.githooks/pre-commit refuses any commit made while main is checked out.

branch=$(git rev-parse --abbrev-ref HEAD)
if [ "$branch" = "main" ]; then
  echo "✗ direct commits to main are blocked…"
  exit 1
fi

Every /fix-it and /feature-it run already respects this without thinking about it — they branch, commit, open a PR, and let GitHub's squash-merge put the change on main. Nothing in that path ever runs git commit with main checked out on anyone's machine.

/ship-it, the release pipeline, was written earlier and differently. Its job is to bump the version in package.json, commit that bump, and tag the result — and npm has a single command that claims to do exactly that:

npm version patch|minor|major

Convenient, and also exactly the kind of shortcut a branch guard exists to catch: it runs wherever you happen to be, and nobody had checked whether “wherever you happen to be” for a release is main.

The idea

npm version <bump> is really three actions wearing a trenchcoat: edit package.json, git commit it, git tag the result. Run it on main and the middle action is exactly what the guard exists to stop — reproduced before touching anything:

npm error command git commit -m 1.0.1
npm error PRECOMMIT RAN (branch=master)

No commit lands, so no tag exists either, so there is nothing to push. The fix is to stop asking one command to do three things and instead put each action where it belongs:

edit package.json on a release/ branch → commit, PR, merge like any other change → tag main’s new HEAD

The npm command itself still does the arithmetic — --no-git-tag-version just tells it to stop there and leave the committing and tagging to us:

npm version patch|minor|major --no-git-tag-version

The commit now happens on a branch, where the guard has nothing to say. The PR goes through the same review and CI as any other change — a release is not special-cased into skipping the checks everything else must pass. And the tag is applied only once that PR has actually merged, to main's real HEAD, by a command that was never a commit to begin with. git tag writes a ref; it does not invoke a commit hook, on main or anywhere else.

Why not just special-case the hook for npm version? Because the guard's whole value is that it has no exceptions to remember. A hook that says “block commits on main, except this one command” is a hook someone will eventually widen by accident. Moving the work to where the rule already applies costs three extra lines; carving a hole in the rule costs a guarantee.

What changed

The seam is entirely inside harness/skills/ship-it/SKILL.md — there is no runtime code here, only the procedure a human and Claude follow together. Step 6 becomes:

git checkout -b release/vX.Y.Z
npm version patch|minor|major --no-git-tag-version
git commit -am "chore: bump version to X.Y.Z"
git push -u origin HEAD
gh pr create …                       # then merge once CI is green

and step 7:

git checkout main && git pull
git tag vX.Y.Z && git push origin vX.Y.Z

README.md's “Releasing ha-card-shared” section carries the same change, so the two copies of this procedure can't drift.

The guardrail is a genuine red–green test even though nothing here is a function. This repo already has a pattern for it — test/skills/claude-shared.test.ts asserts substrings and structure against skill markdown, treating the prose itself as the thing under test. test/skills/ship-it.test.ts follows it: every npm version line inside a bash fence must carry --no-git-tag-version; the doc must name a release/ branch; the git tag step must textually follow a checkout main. All three failed against the old prose and pass against the new.

Verifying past the unit test. A markdown assertion proves the words are right, not that the mechanics hold. The full flow was rehearsed against a real remote: a bare repo, a release branch, a commit, a push, a squash-merge stand-in, a pull, a tag, a tag push — and the branch guard never fired. The first attempt at this rehearsal modeled the squash-merge as a local git commit on main and watched it get blocked, which looked like a finding until the mistake became obvious: gh pr merge --squash executes on GitHub's servers, which never invoke anyone's local core.hooksPath hook. Recorded here rather than quietly discarded — a rehearsal script can be wrong about the thing it's rehearsing.
