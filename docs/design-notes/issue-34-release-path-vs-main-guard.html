Releasing without touching main directly

issue #34 branch fix/release-path-vs-main-guard drafted 2026-08-29 approved

01Symptom

/ship-it could not cut a release. Its step 6 ran npm version patch|minor|major to bump the version, commit, and tag — harness/.githooks/pre-commit blocks every commit whose branch is main, and npm version shells out to a plain git commit. Reproduced in a scratch repo before anything was changed:

npm error command git commit -m 1.0.1
npm error PRECOMMIT RAN (branch=master)

No commit, no tag, no release.

02Root cause

The branch guard and the release step were written by the same design but never checked against each other. pre-commit exists precisely so nothing lands on main except through a reviewed PR — the same discipline every /fix-it and /feature-it run already follows. The release step was the one place still assuming direct-commit access.

03The fix

Split what npm version used to do into three separate acts, put in the right places:

edit package.json (release branch) → commit + PR + merge (same as any change) → tag main (not a commit — guard never sees it)

git checkout -b release/vX.Y.Z
npm version patch|minor|major --no-git-tag-version   # edits package.json only
git commit -am "chore: bump version to X.Y.Z"
git push -u origin HEAD
gh pr create …                                     # then merge once CI is green

git checkout main && git pull
git tag vX.Y.Z && git push origin vX.Y.Z

The version-bump PR is not special-cased — it goes through the same review, CI, and squash-merge as any other change. The tag is applied only after that merge, to main's actual HEAD, and a git tag never invokes a commit hook at all.

04Guardrail

test/skills/ship-it.test.ts — three assertions against the skill's own prose, following the pattern test/skills/claude-shared.test.ts already uses for this repo's markdown procedures: every npm version invocation in a bash fence carries --no-git-tag-version; the doc names a release/ branch; the git tag step textually follows a checkout main. All three red before the fix, green after.

Beyond the unit test. There is no code seam here — this is a documented procedure, not a function. The full release rehearsal was run against a real remote (a bare repo, a release branch, a genuinely server-side squash-merge stand-in, a pull, a tag, a push) and confirmed the branch guard never fires. An earlier version of this rehearsal modeled the squash-merge as a local commit and got blocked — a mistake in the rehearsal script, not a finding: gh pr merge --squash runs on GitHub's servers, which never invoke a local core.hooksPath hook. Recorded so the correction doesn't get lost.

05Non-goals

Weakening the main branch guard itself, or changing what triggers a release (still a pushed vX.Y.Z tag). Only how the version bump reaches main changes.
