Background

Every consumer of this toolchain lives under a strict bargain: check:ci must pass (typecheck, lint, markdown format) and test:coverage must hold 100% statements, branches, functions and lines, or the change doesn't merge. It's enforced twice — a local pre-commit/pre-push pair, and self-check.yml in CI as the real backstop.

The bargain has a blind spot. check:ci's tsc invocation only ever pointed at src/**/*.ts and test/**/*.ts; Biome was only ever invoked as biome check src/ test/. harness/ — the postinstall script that wires every consumer's git hooks and Claude Code config, and the hook that enforces the whole TDD pipeline — sat outside both. Two JavaScript files carrying real conditional logic, checked by nobody's linter, typed by nobody's compiler.

Two corrections before a line of config changed

This issue got two things wrong, and both were caught before implementing rather than after.

The first: it claimed the harness was “never linted, typechecked, or tested.” The testing half was false — roughly 500 lines already existed across test/scripts/setup-claude.test.ts and test/skills/, running in CI on every PR. Scope was corrected down to the two things genuinely missing: lint and typecheck.

The second surfaced mid-implementation. The plan called for widening vitest.config.mjs's coverage.include to catch the harness files under the existing coverage gate. Tried it, empirically, before writing it into the config:

All files          |   25.73 |    20.32 |   51.51 |   27.32
 harness           |       0 |        0 |       0 |       0
  setup-claude.js  |       0 |        0 |       0 |       0

100% dropped to 26%. Not a bug in the files — a structural blind spot in the measurement. Vitest's v8 coverage provider instruments the vitest worker process; both harness scripts are tested by spawning them as real subprocesses, which is the correct way to test a CLI script (it's literally how they run in production, invoked by git hooks and postinstall). A parent process's v8 coverage has no visibility into what a child process executed. Vitest ships no built-in mechanism to merge subprocess coverage back in.

The distinction that mattered: these files aren't untested. They're tested by a method the coverage tool structurally cannot count. Forcing the number to include them wouldn't have made the measurement more honest — it would have broken a 100% invariant this repo treats as load-bearing, for files that were already well covered by a better-suited method. Dropped from scope, and the reasoning recorded so nobody re-proposes it without re-deriving the same 26%.

What shipped

Biome extended to harness/ in both check and check:ci. It found four real, entirely mechanical issues — missing node: import prefixes, unsorted imports, a string concatenation that reads better as a template literal — auto-fixed, zero behavior change.

checkJs (tsconfig.harness.json, allowJs + checkJs + strict, extending the same base config as the main tsconfig.json) was the substantive piece. Turned on cold, it surfaced 30 errors across the two files, almost all one repeating shape:

let payload = {};
// ...
payload = JSON.parse(readFileSync(0, "utf8"));
// ...
const cwd = payload.cwd || process.cwd();
//                  ^^^ TS2339: Property 'cwd' does not exist on type '{}'

An empty-object initializer pins the variable's type to {} for its whole scope — a later reassignment to a JSON.parse'd value doesn't widen it. Every subsequent property read on payload or settings failed the same way. Fixed with two small JSDoc @typedefs — HookPayload for the hook's stdin JSON, ClaudeSettings/GuardHookEntry for the merged Claude settings file — plus @param tags on arrow functions whose parameters had no inferred type. No runtime behavior changed; these are doc comments TypeScript reads.

Two spots needed an actual line, not just a comment: String(tool) before an .includes() call, because tool (payload.tool_name) is legitimately optional and Array.prototype.includes wants its argument to match the array's element type — stringifying first preserves the exact existing behavior (undefined still matches nothing) while satisfying the type. And an inline JSDoc cast on a caught error's .code, since TypeScript treats catch-clause variables as unknown by default and Node's filesystem errors aren't the built-in Error shape.

Not cosmetic. A typed HookPayload is exactly the shape that would make payload.agent_type versus a typo of it impossible to ship silently — the class of bug this whole rebuild keeps catching by hand, one issue at a time.

pre-commit gained npm run --if-present typecheck:harness after the existing typecheck line. The --if-present matters: this hook file is shared with every consumer via core.hooksPath, and only this repo's own package.json defines that script — every consumer silently skips the line, exactly like the existing format:md step above it.

self-check.yml gained python3 -m py_compile on render.py in the lint job: a syntax gate distinct from test/skills/render.test.ts's behavior checks, and the first place the previously undeclared python3 dependency is spelled out explicitly.

Quiz

Why did widening vitest's `coverage.include` to the harness scripts drop overall coverage from 100% to 26%, even though those scripts are tested?

Why does `let payload = {}; payload = JSON.parse(...)` fail typechecking under checkJs + strict, even though JSON.parse returns `any`?

Why does the fix use `String(tool)` before `.includes()` rather than just annotating `tool` as always a `string`?

Why does `harness/.githooks/pre-commit` call `npm run --if-present typecheck:harness` instead of `npm run typecheck:harness`?

During this change, `git checkout -- harness/hooks/skill-guard.mjs` was used to revert an experimental edit and it discarded more than intended. Why?
