Gates for the gatekeeper: lint and typecheck over harness/

issue #35 branch chore/harness-lint-typecheck-gates drafted 2026-08-29 approved

01Problem

The toolchain that enforces 100% coverage and a clean Biome pass on every consumer exempted itself. check:ci covered src/ and test/ only; self-check.yml added actionlint and shellcheck for the two shell hooks, nothing for the JavaScript. harness/setup-claude.js and harness/hooks/skill-guard.mjs were never linted or typechecked.

Correction, made against this same issue before implementing it. The original text also claimed the harness was “never…tested”. False — test/scripts/setup-claude.test.ts and test/skills/ already held ~500 lines covering the installer, the CLAUDE-SHARED.md contract, and render.py. Scope was cut to what's actually missing: lint, typecheck, and the render.py syntax gate. skill-guard.mjs's own tests move to #36, alongside its rewrite.

02A second correction, found while implementing

The issue also asked to widen vitest.config.mjs's coverage.include to harness/**/*.{js,mjs}. Tried it first, empirically:

All files          |   25.73 |    20.32 |   51.51 |   27.32 |
 harness           |       0 |        0 |       0 |       0 |
  setup-claude.js  |       0 |        0 |       0 |       0 | 1-166
 harness/hooks     |       0 |        0 |       0 |       0 |
  skill-guard.mjs  |       0 |        0 |       0 |       0 | 2-107

Coverage dropped from 100% to 26%. The reason is structural, not a bug: vitest's v8 provider instruments only the vitest worker process. Both harness scripts are tested by spawning them as real subprocesses (execSync('node setup-claude.js')) — the correct way to test a CLI script, and how they're actually invoked in production — and v8 coverage inside the parent process has no visibility into a child process's execution. Confirmed against the vitest docs: no built-in mechanism merges subprocess coverage. Widening include as specified would not have made the gate more honest; it would have broken the 100% threshold this repo treats as a headline invariant, for files that are thoroughly tested by a method the tool simply can't see.

Dropped from scope. Left as a real gap, correctly attributed: not “untested,” but “tested by a method vitest's coverage can't count.”

03What shipped

Biome over harness/ → checkJs over harness/**/*.{js,mjs} → py_compile on render.py → all three wired into check:ci and pre-commit

Biome found four real, all-mechanical issues across the two files — missing node: import prefixes, unsorted imports, string-concatenation where a template literal reads better — auto-fixed, zero behavior change.

checkJs was the substantive part. Turning on strict + checkJs against genuinely untyped JS surfaced 30 errors, almost all one shape: a JSON-parsed value (payload, settings) declared with an empty-object literal, so TypeScript pins its type to {} and every later property read on it fails. Fixed with two small JSDoc @typedefs — HookPayload for the hook's stdin JSON, ClaudeSettings/GuardHookEntry for the merged settings file — plus per-parameter @param tags where an arrow function's parameter had no inferred type. No runtime code changed; only doc comments were added, with two exceptions: String(tool) before an .includes() call (tool can be undefined; stringifying it first keeps the existing behavior and satisfies the type), and an inline JSDoc cast on a caught error's .code property, since TypeScript treats catch-clause variables as unknown by default.

These weren't cosmetic misses. A typed HookPayload is exactly the shape that would have made payload.agent_type vs. a typo impossible to ship silently — the class of thing this whole rebuild keeps finding by hand.

pre-commit now runs npm run typecheck:harness alongside the existing typecheck, guarded by --if-present — this hook file is shared with every consumer via core.hooksPath, and only this repo's own package.json has that script, so consumers silently skip it, exactly like the existing format:md line.

self-check.yml gained python3 -m py_compile on render.py in the lint job — a syntax gate distinct from test/skills/render.test.ts's behavior checks, making the previously undeclared python3 dependency an explicit, fast-failing CI step.

04Guardrail

Verified live rather than added as a new test file, since check:ci running in CI on every PR (self-check.yml) already is the regression mechanism. Proved it catches a real error before shipping: introduced payload.nonexistent_field in skill-guard.mjs, confirmed tsc -p tsconfig.harness.json reported TS2339 and exited non-zero, reverted, confirmed clean again.

A process note, for the log. The first attempt at that proof used git checkout -- harness/hooks/skill-guard.mjs to revert the injected error — which, since nothing on this branch had been committed yet, reset the file all the way back to main's version and silently discarded every JSDoc edit made earlier in the same session. Caught immediately by diffing against HEAD, redone from scratch, and the revert step redone using Edit (a targeted string replace) instead. Recorded rather than smoothed over, and it's the reason git add -A ran immediately afterward, before anything else — uncommitted work on a fresh branch has no safety net.

05Non-goals

Restructuring setup-claude.js or skill-guard.mjs to be importable-and-unit-testable in-process, which would make v8 coverage see them. That's a real option, but it changes how these scripts are shaped, and #36 already plans to rewrite skill-guard.mjs's core logic — better to let that rewrite decide the shape than to force one here first.
