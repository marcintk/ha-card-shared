Background

Every tool call Claude makes in this repo — an Edit, a Bash command — passes through a PreToolUse hook before it runs: Claude Code serializes the call into JSON, pipes it to a configured script on stdin, and only proceeds if that script exits 0. Exit 2 blocks the call outright. This repo's hook is harness/hooks/skill-guard.mjs, and its job is to let a subagent do its assigned job and nothing else — a test-writer that can't touch src/, a reviewer that can't ship, a coder that can't skip the red step of red-green.

The hook had two independent halves. A role half keyed on agent_type — which subagent is running — worked correctly and had four real bugs. A skill half keyed on which pipeline skill (/fix-it, brainstorm-it, ...) was active, recorded by one hook and erased by another, had never worked at all.

Why the skill half was dead, and what replaces it

Claude Code fires a Stop hook whenever Claude finishes responding — that is, at the end of every turn, not at the end of a task. The old design used Stop to erase the recorded active skill:

PreToolUse × Skill → record skill in one file → Stop → delete it — on every single turn

A pipeline like brainstorm-it is designed to be multi-turn — “ask one question at a time, wait for the answer.” The recorded skill was gone before the second question was even asked. The policy file's stale_seconds: 1800 setting implied the intended lifetime was thirty minutes; the actual lifetime, in practice, was one response.

The fix removes the erase-on-every-turn mechanism entirely and replaces it with something a skill sets on purpose, not something a hook infers and forgets:

skill-guard.mjs phase design|code|ship|release
skill-guard.mjs phase clear

Written to .claude/skill-guard/phase with an 8-hour expiry — long enough to outlast a real multi-turn session, short enough that a forgotten phase doesn't linger across unrelated work days later. No hook writes or erases it automatically; only an explicit phase call does. (No entry-point skill calls it yet — that's the next issue in this sequence. This one builds and fully tests the mechanism it will use.)

With a phase and a role both potentially active at once, the natural question is which one governs. The answer here is neither, alone: a call is denied if either denies it — a union. Under phase code (which allows a plain commit), a subagent whose role forbids commits unconditionally still gets denied. Neither side can be a loophole for the other.

The role-side bugs, and what closed each one

Reviewer. One line: deny_write: ["^test/", "\\.test\\.ts$"] instead of the blanket ["."], so the role's stated job (“read-only except for what /simplify applies”) is now what the policy actually enforces.

Coder's TDD gate, rebuilt as a marker. The old gate ran the entire test suite inside the hook on every src/ write, to infer whether a red test currently existed:

execSync('npx vitest run --silent --reporter=dot', { cwd: dir, stdio: 'ignore' });

Beyond the deadlock (the moment the first edit turned the target test green, every further write that slice was refused — and fixing a second file or a reviewer follow-up needs more than one write), this ran inside a 30-second PreToolUse budget, so a slower suite made the check silently time out and stop enforcing anything, and any unrelated failure (a missing dependency, a config error) read as “red” and let a write through it shouldn't have. Replaced with an explicit marker:

skill-guard.mjs red test/foo.test.ts   # a test exists and is failing
skill-guard.mjs green                  # the slice is accepted; clear it

pipeline-coder may write src/ only while the marker is present, and it too expires (30 minutes) so a forgotten marker can't leave the gate open indefinitely. No subprocess, no timeout risk, no misread exit code.

Path normalization. The old check was raw.startsWith(cwd) — a literal string-prefix test. It fails exactly when the two strings represent the same directory without being the same string: a symlinked checkout, or (this session's own working directory, as it happens) a path with a stray double slash. When it fails, the path never gets stripped to project-relative, so a pattern like ^src/ stops matching — while a blanket ["."] rule, which doesn't care about the prefix, keeps working. The guard degrades unevenly and invisibly.

function toProjectRelativePath(raw, root) {
  const absTarget = isAbsolute(raw) ? raw : resolve(root, raw);
  const realRoot = realpathSync(root);        // canonicalize both sides
  const realTarget = realpathTolerant(absTarget);  // ...even a not-yet-created file
  const rel = relative(realRoot, realTarget);
  if (rel === ".." || rel.startsWith(`..${sep}`)) return null;  // outside root
  return rel.split(sep).join("/");
}

realpathTolerant exists because Edit/Write targets often don't exist yet — it walks up to the nearest real ancestor, canonicalizes that, and reattaches the segments still being created. A target that resolves outside the project root is now denied unconditionally, under any guarded context — independent of whether some specific deny_write pattern happens to match a path like ../../../etc/passwd, which none of them would.

deny_bash. Every pattern in the policy was anchored: ^\s*git\s+(commit|push)\b. An anchor means “only at the very start of the string” — so cd /tmp && git push, env FOO=bar git push, and bash -c 'git push' all put the denied command somewhere other than position zero and passed clean through. Dropping the anchor is the whole fix for those three; a fourth case (git -C <dir> commit) needed one added step, since the flag sits between git and the subcommand rather than around the whole line:

cmd.replace(/\bgit(?:\s+-C\s+\S+|\s+-c\s+\S+=\S+)+/g, "git")

This remains a guardrail, not a sandbox — the code comments say so explicitly now. A sufficiently determined script could still route around a regex-based check. What changed is that the four bypasses this audit actually found are closed.

Quiz

Why did the old skill-layer guard provide essentially no protection, even though it was clearly coded and its policy file looked correct?

Under the new union resolution, phase `code` allows a plain `git commit`. If the active subagent's role forbids commits unconditionally, what happens?

Why did the old suiteGreen() TDD check deadlock a slice after its very first successful edit?

Why does the new path check deny a target outside the project root unconditionally, rather than relying only on each role's deny_write patterns?

Why does removing the `^\s*` anchor from deny_bash patterns, by itself, defeat `cd /tmp && git push` and `bash -c 'git push'`, with no other change needed?
