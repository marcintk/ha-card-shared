Background

Before this change, making any change to a card repo meant typing one of two commands: /fix-it <n> for a bug, /feature-it <n> for everything else — a new export, a chore, a one-line dependency bump. The two skills were near-mirrors: read the issue, investigate, design (or reproduce), write a red test, implement, review, ship. The only real difference was the first move — fix-it jumped straight to reproducing; feature-it ran a design grill first.

That mirror-image duplication is exactly the shape that drifts. Two files describing almost the same procedure will, over enough small edits, describe two slightly different procedures — and the human typing the command has to correctly guess, in advance, which of the two mirrors is more accurate for the change in front of them. A one-line dependency bump: bug or feature? A behavior change discovered while fixing a typo: does it become part of the fix, or does someone stop and re-file as a feature?

This issue collapses that choice away, and does one more thing at the same time: it wires up a mechanism the previous issue in this sequence (#36) built and fully tested, but nothing was calling yet.

One pipeline, four checkpoints

The new shape is a straight line with four named stops, each one a thing a human types:

/design-it <n> → /code-it <n> → /ship-it → /release-it

The bug/feature fork doesn't disappear — it moves inside /design-it, where it belongs: the skill's own early steps (grep LESSONS.md for the problem class, then a pipeline-explore subagent that either reproduces a bug or scans prior art for a feature) branch on what the issue actually turns out to be, from evidence gathered in the moment — not from a guess made before anyone looked.

A rename rides along inside the same table that made this collapse legible. The old /pr-it — an AI-invoked sub-skill nobody ever typed, doing commit → push → PR → merge — is promoted to a human-typed entry point and takes the name /ship-it. The old /ship-it — bump semver, tag, publish a draft release — is renamed /release-it, to make room. Read the acceptance criteria's own end-to-end sequence without knowing this and it looks backwards: /ship-it now happens on every single change; /release-it happens rarely, batched across several.

Two new things, not just four renamed old ones. /design-it gained a rule it's built around, not bolted onto: it does not converge on a single approach early. For anything non-trivial it runs design it twice — at least two materially different approaches, written out and compared, before either is judged — and closes with an adjacent-opportunity pass: before locking in, name what this change makes cheap, what it forecloses, and split anything else worth doing into its own issue rather than quietly widening this one's scope.

What changed

The four files, 199 lines combined, replacing four totalling 223 — a net reduction despite adding two new steps to design-it and phase-wiring to all four. No file exceeds 69 lines.

Phase wiring, the payoff of #36. #36 built skill-guard.mjs phase <name> and tested it thoroughly, but explicitly deferred calling it as its own non-goal — no skill existed yet to call it from. Each of the four skills now opens with exactly that line: design-it sets phase design, code-it sets phase code (and wraps each slice in red/green), ship-it sets phase ship, release-it sets phase release. The mechanism goes from tested-but-inert to actually governing what each phase of a real run may do.

Approval moved earlier, and split in two. Under the old model, a design note's status flipped to approved exactly once, right before the PR — so the badge could mean either “the plan is sound” or “this code is about to ship,” and in practice only ever meant the second, since nothing set it before code existed. explain-it gained a new approve phase, called by design-it the moment the human accepts the design — before any code is written. Its existing finalize phase, now called later by ship-it once there's an actual diff, stopped touching the status badge entirely; it only renders the explain-diff and fills in the note's Explain-diff link.

## approve <n> <slug>
design-it calls this once the human approves the design, before any code exists.
Status badge → approved. Does not touch the explain-diff — that's finalize, later.

A small ordering bug came free with that split: the old finalize claimed to fill in the design note's PR link in the same step that rendered the explain-diff — but at that point in the old flow, the PR didn't exist yet (pr-it open ran afterward). The new ship-it fills that link itself, one step later, once gh pr create has actually returned a number.

Verified beyond the file diffs. A real setup-claude.js run against a scratch consumer confirms exactly ten skills get symlinked, with none of the three retired ones present. A second run, with a stale fix-it symlink planted first to simulate an actual upgrading consumer, confirms it gets pruned automatically — by code that already existed, built for exactly this case (“a skill removed in a newer version”), never touched by this issue.
