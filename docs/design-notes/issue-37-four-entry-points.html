Design note · ha-card-shared

Four verbs: collapsing nine skills to design-it, code-it, ship-it, release-it

issue #37 branch refactor/four-entry-points drafted 2026-08-29 approved

01Problem

Nine skills, and a split that never earned its keep: /fix-it for a bug, /feature-it for everything else, with near-identical steps duplicated between them and a judgment call at the door (“is this really a bug or a small feature?”) that nobody needed to make. No single artifact a change lived in — the design note existed, but the GH issue body was also called “the state store,” and neither had a resumable, reopenable shape.

02The collapse

/design-it <n> → /code-it <n> → /ship-it → /release-it

OldNew
fix-it + feature-it (design half)design-it
fix-it + feature-it (TDD half)code-it
pr-itship-it (renamed & promoted to a human-typed entry)
ship-it (release)release-it (renamed)

The bug/feature judgment call is gone — /design-it takes any GH issue, and its own first steps (grep LESSONS.md, then either reproduce or scan prior art) already branch on what the issue actually is, without the human pre-classifying it at the command line.

A genuine rename hid inside the collapse. The table in the issue names the new /ship-it as “commit, PR, explain-diff comment, CI, squash-merge” — that was the old pr-it's job, an AI-invoked sub-skill nobody typed directly. The old /ship-it — bump semver, tag, release — becomes /release-it. Two skills swapped names as part of the same change; get this backwards and the acceptance criteria's own end-to-end sequence (design-it → code-it → ship-it → release-it) stops making sense.

03What's new, not just renamed

/design-it is built to not converge early. Two additions beyond what fix-it/feature-it did: design it twice — for anything non-trivial, at least two materially different approaches, written out and compared, before either is judged (the existing codebase-design skill already had a DESIGN-IT-TWICE.md companion note describing exactly this pattern; referenced, not re-explained) — and an adjacent-opportunity pass: before converging, name what this change makes cheap and what it forecloses, and split off anything worth doing separately into its own issue rather than folding it in.

Phase wiring, finally. #36 built skill-guard.mjs phase and fully tested it, but nothing called it — explicitly deferred as that issue's non-goal. Each of the four skills now opens with exactly that call: design-it → phase design, code-it → phase code (plus red/green around each slice), ship-it → phase ship, release-it → phase release. The guard's role half was already live; this makes the phase half live too.

The approval moment moved. Under the old model, a design note's status flipped to approved once, right before the PR — conflating “the plan is good” with “the code shipped.” Under the new one, /design-it approves the plan, before any code exists; explain-it gained an approve phase to do exactly that, and its finalize phase (called by /ship-it, once there's an actual diff) no longer touches the status badge — it only renders the explain-diff and fills in the README's Explain-diff link. The PR link fills in one step later, inside /ship-it itself, once gh pr create actually returns a number — the old flow's finalize claimed to fill that link too, one full step before the PR it was linking to existed.

04Staying small

Four files, 199 lines combined — against 223 for the four they replace (fix-it 58 + feature-it 62 + pr-it 35 + old ship-it 68), despite adding design-it-twice, the adjacent-opportunity pass, and explicit phase wiring throughout. No file exceeds 69 lines; the constraint asked for “roughly under 80.” No references/ directory anywhere — every procedure a skill needs lives in its own body or is one line pointing at an existing companion note (DESIGN-IT-TWICE.md), never a subtree of its own to load.

05Guardrail

test/skills/claude-shared.test.ts now asserts the acceptance criteria directly: all four entry points exist and carry disable-model-invocation: true; fix-it, feature-it, and pr-it are confirmed gone (not just untested); each entry point's SKILL.md is ≤85 lines; none adds a references/ directory. test/skills/release-it.test.ts (renamed from ship-it.test.ts, retargeted) keeps #34's release-flow assertions pointed at the file that now actually owns that flow, and gained one more: ship-it/SKILL.md must never again contain the string "npm version" — a tripwire against the two skills quietly re-merging later.

Live-verified, not just asserted: a real setup-claude.js run against a scratch consumer shows exactly the ten intended skills symlinked, none of the retired three present; a second run with a stale fix-it symlink planted first (simulating a real upgrading consumer) confirms it's pruned automatically — the existing broken-symlink cleanup, built originally for “a skill removed in a newer ha-card-shared,” doing exactly the job it was built for.

06Non-goals

A full autonomous live dogfood of the new chain on a real issue (/design-it through /release-it). brainstorm-it's whole design is a human interview, one question at a time — genuinely running it requires the user's real engagement, not something to simulate mid-sequence. Structural correctness is verified above; the live run is the user's to invoke whenever they pick up the new pipeline.

The v1.4.1→2.0.0 recipe. This is consumer-breaking (/fix-it and /feature-it disappear from their .claude/skills/), so the recipe does need a migration line — added once #33–#38 are ready to ship as one release, matching the deferral already recorded in #35 and #36's notes.
