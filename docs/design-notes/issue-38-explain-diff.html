Background

The last issue in this rebuild is a batch of small, unrelated defects the original audit found and deliberately didn't split into their own issues — each one real, but none big enough to earn a design note of its own. The pipeline's own acceptance bar for a batch like this is explicit: each item fixed, or explicitly declined with a reason. Declining is a legitimate outcome, not a shortcut, provided the reason is checked rather than assumed.

The staging fix, and the bug hiding inside the first attempt at it

git commit only commits what's staged — the index, not the working tree. A hook that runs an auto-fixer (Biome, Prettier) after staging has a real problem: the fixer edits files on disk, but those edits aren't in the index yet, so the commit would ship the pre-fix version unless something re-stages them.

The old fix was git add -u — "stage every modification to every tracked file." That solves the immediate problem and creates a worse one: if anything else in the working tree happened to be dirty — an experiment you hadn't finished, a file you were mid-edit on for something unrelated — it rides along into this commit too, silently.

The fix sounds simple: remember what was staged before the fixer runs, then only re-stage that. The first way to write it wasn't simple enough:

staged=$(git diff --cached --name-only -z)   # NUL-separated, for filename safety
# ...
printf '%s' "$staged" | xargs -0 -r git add

This looks careful — NUL-separated output is the standard defense against filenames containing spaces or newlines. It also doesn't work, and the failure is silent. A POSIX shell variable is, under the hood, a NUL-terminated string; the moment `git diff -z`'s NUL byte lands inside one via $(...), the value is corrupted — no error, no warning, just a variable that no longer contains what you think it does.

Caught by rehearsing, not by reasoning about it harder. A quick manual test — stage one file, leave a second one modified-but-unstaged, run a fake auto-fixer that edits both, apply the fix, check what actually got staged — came back empty. Nothing was re-added. That's the entire value of testing a shell one-liner before trusting it: the bug was invisible from reading the code, and obvious the moment it ran against real files.

The fix: skip the shell variable for the NUL-separated data entirely.

staged=$(git diff --cached --name-only)      # plain newlines — fine here
# ...
printf '%s\n' "$staged" | git add --pathspec-from-file=-

--pathspec-from-file=- reads the path list straight off the pipe; nothing NUL-shaped ever has to survive a round trip through a shell string. Re-rehearsed, and this time the isolation held: the staged file's index picked up the fixer's change, the unstaged file's index stayed byte-identical to HEAD, even though the fixer had touched its working tree too.

The other three items

Handoff files, relocated. explain-it finalize wrote to /tmp/explain-spec.json and /tmp/issue-<n>-explain-diff.md — a directory shared machine-wide across every sibling card repo this toolchain serves, gone the instant the session ends. Moved to docs/design-notes/.work/, gitignored, scoped to the one repo the handoff is actually happening in. Confirmed live: a file written there produces empty git status --porcelain output.

Two doc-drift items needed no fix at all — checked, not assumed. skill-guard.json's stale “SOLUTIONS.md” reference and README's “tdd-coder” subagent name were both already corrected earlier in this same rebuild sequence (#36 and #37, respectively), before this issue ever got to them.

One real fix, one real clarification. commit-it's mandated trailer hardcoded Claude Sonnet 5 regardless of which model actually wrote the commit — changed to an instruction to substitute the model in use, never a fixed name. CLAUDE-SHARED.md's command block lists build:prod, dev, test:watch — true that none of these exist in ha-card-shared's own package.json, and not actually a bug: checked all four sibling card repos, and every one of them defines exactly these scripts. The block was describing a card's convention all along, correctly, just without saying so — one clarifying line fixes the ambiguity without touching the commands themselves.

Declined, with the claim verified first. setup-claude.js's linkInto swallows EEXIST silently, so an existing symlink is never re-pointed at a new target — the issue itself proposed declining this, calling it “covered incidentally by the install fixture matrix.” Checked rather than trusted: test/scripts/setup-claude.test.ts's existing “running twice does not throw on existing symlinks” case does in fact exercise this exact path. The claim held, so the decline stands — harmless while every symlink target is a stable absolute path, a real trap only if the layout moves, which nothing in this rebuild does.
