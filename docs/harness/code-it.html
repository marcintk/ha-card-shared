Inside code-it

01

What it does

Never runs ahead of /design-it: a missing or unapproved note means stop and point back at it, not infer one. The work is a loop over the slices the note declared. Each slice is a strict red → green → review → accept cycle, and the same - [ ] / - [x] discipline applies to every step.

02

The shape of a run

Setup runs once; the slice cycle runs once per declared slice; the coverage gate closes the phase. Local commits are allowed here and nowhere else in the pipeline before /ship-it.

03

The slice cycle — and the marker that gates it

The red marker file is not a reminder. It is the precondition skill-guard checks before it will allow code-writer to write anything under src/.

04

What it uses

Three sub-agents with deliberately narrow briefs, one sub-skill for the record, two slash commands, and the same hook as design-it — in a different phase, with an extra per-slice marker.

Guardrail hook

harness/hooks/skill-guard.mjs
· skill-guard.json Phase code allows git commit but denies push / pr / version. On top of the phase, the red / green sub-commands write and clear a per-slice marker; the tdd rule denies any src/ write while no marker is set. Marker expires after 30 min.

Sub-agents

harness/agents/test-writer.md Writes exactly one test that fails on current code, then stops. Given the public seam and expected behavior — nothing about the fix. Hook blocks any write under src/.
harness/agents/code-writer.md Implements the smallest change that passes the failing test, then stops. No speculative behavior. Hook blocks edits to test/ and *.test.ts, and blocks src/ until the slice is marked red.
harness/agents/reviewer.md Runs /code-review then /simplify on the accepted slice. Correctness findings need a concrete failing input. Does not redesign, does not expand scope. Hook blocks git and gh from this role.

Sub-skill

harness/skills/explain-it slice updates the design note with what each slice changed; compound prepends a deduped "symptom → root cause → guardrail" entry to LESSONS.md, or no-ops when a slice taught nothing reusable.

Slash commands

/code-review Run by the reviewer agent at 4.6 — correctness bugs plus an over-engineering pass.
/simplify Run straight after — applies reuse / altitude / efficiency cleanups, no behavior change.

Inputs & tooling

docs/design-notes/issue-<n>-<slug>.html The approved note. Its declared slices are the work list; its seams and expected behaviors are what test-writer is handed.
LESSONS.md Re-grepped at step 2 for the problem class; appended at 4.8 via explain-it compound.
npm run test:coverage · git The 100% coverage gate at step 5; the branch and the local per-slice commits.
05

How it addresses the task

The task is to turn an approved design into working code without the implementation drifting from the design or accreting over-engineering on the way. Six choices do that work.

a The note is the contract

An unapproved or missing note stops the skill — it will not infer one. Slices come from the note, in the note's order. Implementation cannot quietly redefine the design.

b Red before green, enforced by a hook

No src/ write exists until a test is failing for the right reason. The order is not a convention you can forget under pressure — it is a marker file the hook checks on every edit.

c The two writers are kept ignorant of each other

test-writer never sees implementation reasoning; code-writer never edits tests. The test asserts behavior through the seam from an independently sourced expected value — so it can't be shaped to fit the code.

d Over-engineering gets a dedicated pass

Every slice runs /code-review's over-engineering check and /simplify before a human sees it — reinvented stdlib, needless indirection, speculative flexibility, dead config.

e Three strikes → back to design

A slice that fails review three times is a design problem, not a patch problem. The skill routes it to /design-it <n> rather than accreting a fourth attempt on a bad shape.

f Coverage cannot regress

The phase does not end — and /ship-it does not begin — until npm run test:coverage is back at 100%.
